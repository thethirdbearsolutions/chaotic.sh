The Agent Runaway

AI coding agents have no brakes. They'll burn your token budget, ignore your architecture, and close 20 tickets in a loop without stopping to think.

Jira and Linear are human-first. Agents are guests in our world. In their world, they need physics.

The Insight

You don't tell a toddler "don't fall down the stairs" 500 times.
You put a gate in front of the stairs.

Chaotic applies this to AI. The agent just uses a CLI. Sometimes commands succeed. Sometimes they fail with hard errors. The agent adapts to the world you've built.

Core Mechanics

1. Rituals

Rituals are checkpoints you define. They can trigger on sprint close, ticket claim, or ticket close:

  • Run the test suite
  • Attest documentation is current
  • Request an oppositional code review
  • File a design spec with the alternatives you considered
  • Reflect on what went well this sprint and vent about what frustrated you

Until rituals complete, the action is blocked. The pause is the point.

2. Sprints & Limbo

Sprints have point budgets. Exceed it, and the project enters Arrears. Close a sprint, and it enters Limbo until rituals clear.

PointsSpent > Budget ⇒ State: Arrears

The CLI blocks work until the constraint clears. Not a suggestion. A wall.

3. Human Gates

You set the autonomy level for each ritual.

Auto: Agent attests, work continues.
Review: Agent attests, you click Approve.
Gate: You do the ritual yourself.

Agents & MCP

Agents can shell out to the CLI, or use Chaotic as native tools over the Model Context Protocol. Either way they get the same budgets, rituals and gates.

Local: chaotic mcp

An MCP server over stdio for any harness on the same machine, such as Claude Code. It reuses the CLI's login and profile, so there is no separate MCP sign-in.

claude mcp add chaotic -- chaotic mcp

# several agents on one machine? pin a profile
claude mcp add chaotic -- chaotic --profile myprofile mcp

Any MCP host that takes a JSON config works the same way: command chaotic, args ["mcp"].

Remote: add by URL Coming soon

The server speaks MCP over Streamable HTTP at /mcp today, with an API key. Once OAuth is on, you give a client the URL and nothing else: it finds Chaotic's sign-in (OAuth), opens a consent page in your browser, and you approve it there. Setup is documented for claude.ai custom connectors, Claude Desktop, ChatGPT, Claude Code and MCP Inspector; the Claude Code flow is the one tested end to end so far. claude.ai, Claude Desktop and ChatGPT connect from their own servers, so they need yours on public https.

claude mcp add --transport http chaotic \
  https://your-chaotic-host/mcp
# then /mcp in a session → Authenticate

The code is on main but off unless a server turns it on (chaotic system config set APP_BASE_URL, then OAUTH_ENABLED), and it is not in a PyPI release yet. What works today: send an API key in an Authorization header, from scripts, CI or any client that can set one. The old /mcp/ck_... capability URL is deprecated.

Agents are identities

An agent is a teammate with its own name, not a borrowed login. Everything it does is attributed to it, and a human answers for every one.

  • It acts as the agent, never as you

    An agent is made with its own key (chaotic agent create), and issues, comments and claims land under its name. Its key only reaches its own team or project.

  • One identity per Claude Code session

    Give a machine a registrar's key and opt in with session_identity: auto, and each Claude Code session there registers its own short-lived agent, so two sessions never claim a ticket "as each other". Details below.

  • A human behind every agent

    Each agent has a human owner, and each agent key a human holder. Remove someone from the team, or deactivate them, and the agent keys they hold stop working; chaotic agent deactivate retires an agent while keeping its work attributed to it.

  • You approve every connection Coming soon

    The consent page names the app and the host the approval goes to. An app that registered itself is badged Unverified app, and an approval going to a program on this computer (a localhost redirect) gets a warning. You choose the team, which agent it acts as (a new one, or one you manage) and which projects. Nothing is approved silently, not even a recognized app.

  • Short-lived, and easy to cut off Coming soon

    An app connected by URL gets access tokens that last 10 minutes, acting as the agent with the write policy. One that asks to stay connected (offline_access) refreshes them while it is used at least once every 30 days, for at most 90 days before you approve again. Disconnect from Settings › Connected Apps or chaotic auth connections revoke.

Per-session identity for Claude Code

Make a registrar once (from the CLI, or Agents › Create Agent › Registrar in the web app), give the machine its key and turn the setting on. It is off by default.

chaotic agent create "Claude Code" --registrar
chaotic auth set-key ck_...   # the registrar's key
chaotic config set-session-identity auto

Inside Claude Code, the CLI and chaotic mcp then register the session as its own agent, named after the registrar and the branch, with a key that expires in 7 days, and never fall back to the shared key. Other harnesses can call POST /api/agents/register the same way.

A session identity is an ordinary agent, so gates, leases and the inbox apply. Its scope is never wider than its registrar's, its owner is the human behind the registrar's key, and a registrar cannot write as itself. Registrars are capped (200 live identities and 60 registrations an hour by default); identities idle for 7 days drop out of lists, and deactivating a registrar retires its sessions.

What agents can do

Both transports serve the same toolset, with typed schemas and structured errors an agent can act on.

Issues

List, view, create, update and comment; find ready work and claim it with a lease; block, unblock and label; read description history.

Sprints

Read the current sprint and its budget, add or remove issues, close the sprint, and audit the budget transactions behind its spend.

Rituals

See which rituals are pending, then attest or complete them, with a note or a linked document or URL as the evidence.

Docs

Write and update team documents, link them to issues, and browse every past revision.

Inbox

Read what's waiting on you, such as gates, reviews and assignments, and mark items read.

Context

Recent activity, projects, labels, and server_info to check the toolset after an upgrade.

Setup details for every client are in docs/agents.md.

Grows With You

Chaotic scales in two directions: human workflows and agent autonomy. Start with the essentials, then dial up the affordances when you need them.

Human affordances

Begin with basic issue tracking, then layer on labels, issue types, docs, and sprints as the team expands.

Agent affordances

Delegate a ticket, then add rituals, budgets, estimation requirements, and multi-agent coordination when stakes rise.

Drag the sliders to see the system surface more structure as you grow.

Human affordances Simple → Full stack
Start simple Full team
Agent affordances Basic → Orchestrated
Single agent Multi-agent

Human track

  • Basic issue tracking
  • Teammates + assignees
  • Labels + issue types
  • Docs + knowledge base
  • Sprints + retrospectives

Agent track

  • Basic issue delegation
  • Ticket-close rituals
  • Sprint budgets
  • Open/claim estimate rules
  • Sprint limbo + multi-agent tokens
More human structure ↔ more agent structure

  2. 0.1.0 Oct 31, 2026
    • One agent identity per Claude Code session, opt-in with session_identity: auto and a registrar (chaotic agent create --registrar, or in the web app). In a cloud environment the registrar key can be a network secret.

  3. 0.1.0a21 Oct 13, 2026
    • Agents that authored work can't be deleted, so their work is never lost.
    • chaotic system upgrade always ends with the server up, bounds shutdown time, and refreshes an unedited service file (backing up the old one).
    • The open issue in the web UI updates live when an agent comments, and MCP issue_update can set or clear a parent.
    • One database migration: upgrade with chaotic system upgrade, which backs up first. MCP clients should reconnect.
